## Context

`clinic_answer` / `tip_answer` 已注入喂养记录、`chat_context` 与知识，但 system 对建议题写「记录只作背景」，user 收尾仅「闺蜜口语」，模型常空共情。产品要求：像有经验的闺蜜；回应时点名「上次说了什么」或「历史喂养了什么」再对应作答；有据不凭空；约 50 字内可达成。闲聊跳过检索等路由优化明确不做。

## Goals / Non-Goals

**Goals:**

- 改 clinic（必做）与 tip（同气质）提示词，落实有据点名 + 短回复。
- 有 `chat_context` → 正文点上轮相关；有 `history_events` → 点最相关 1 条记录事实。
- 无对话且无记录 → 不编「上次/记录里」。
- 保留点查念时间、汇总看趋势、不诊断/不处方等安全规则。

**Non-Goals:**

- 不改 LangGraph 边、needs_history、向量门槛、Q&A 捷径逻辑。
- 不强制对 `qa_hit` 捷径答案二次润色（捷径不走本提示；文档标明例外）。
- 不做回复后置校验（字数/是否点名）的程序化 gate（靠提示约束）。

## Decisions

### 1. 仅改提示词，不改编排

- **选择**：更新 `build_clinic_answer_system_prompt` / `build_clinic_answer_user_message` 与 tip 对等函数。
- **理由**：依据已在 user message；缺的是行为约束。
- **备选**：后置 LLM 检查是否点名 — 拒绝，成本高且与 50 字目标无关。

### 2. System：有经验闺蜜 + 有据必点

System 增加明确块（大意）：

1. 像带过娃的闺蜜：接情绪 → 点依据 → 轻提醒；不端、不科普腔。
2. 有近期对话：必须点到上次相关一句（意译即可），再答本轮。
3. 有喂养记录：必须点到与本轮最相关的 1 条（时间/次数/间隔等），再对应回应；禁止只共情不碰数据。
4. 两者都无：禁止编造「上次/记录」；可短陪。
5. 全文约 50 字内；只挑一条依据，不堆砌。
6. 冲突：记录与口述不一致时以记录为准，口语圆一下。

删除或改写「闲聊/建议：知识与记录只作背景」。

### 3. User 收尾条件化

- 有 history 块 / chat 块时，收尾显式写「必须结合…点名…」。
- 皆无时写「不要编造上次或记录」。
- 点查/汇总保留「必须以记录为准」；与 50 字：点查/汇总若需念清时间，允许略超，但建议题严格约 50 字——**产品确认建议题 50 字含点名；点查/汇总可略长以念清时间**（与现提示一致）。

### 4. Tip 对齐

- Tip system/user：记事件后开口时，有近史则点一条近况；有 chat 则接上；约 50 字；无据不编。

### 5. Q&A 捷径例外

- 命中捷径直接返回库中答案，本 change 不包一层「有据点名」；若后续要统一，另开 change。

## Risks / Trade-offs

- [模型仍空共情] → 收尾用「必须/禁止」强约束；可加一条 few-shot 示意（可选，控制 token）。
- [50 字与点名打架] → 只允许 1 条依据；点查/汇总明确可略长。
- [无数据时过干] → 允许短共情，禁止假记忆。
- [捷径答案风格不一致] → 接受为例外并在 tasks 注明。

## Migration Plan

1. 部署新提示词即可；无迁移。
2. 回滚：恢复旧 prompt 字符串。
