## Context

预测快照是 Redis 键 `predict_algo:{设备}`，TTL 600 秒，内容是 `by_root`。问预测时按根读快照，没有或还原失败才拉近 7 日历史并重算，且只在 `status=ok` 时 `put_root`。

Python 落库成功会 `delete` 整份键。前端也能直接改记录，那次改动不会经过这段删除，所以不能把「增删改时重算并写回」当成唯一新鲜来源。兜底 `soft_reply_for_miss` 只读快照，空则在提示词里写「无预测算法快照」，不重算。

## Goals / Non-Goals

**Goals:**

- 兜底发现没有快照时，先生成再把结果放进同一次回答。
- 已有快照时不重算，让未改数据在 10 分钟内自然过期。
- 落库成功仍删除整份快照。

**Non-Goals:**

- 不在增删改时重算或写回快照。
- 不改问预测的命中、预约和下一次时间逻辑。
- 不缩短或延长 TTL。
- 不在前端改记录时主动失效。10 分钟内前端改过的数据，兜底仍可能读到旧快照，直到过期或被 Python 落库删掉。

## Decisions

1. **只在整份缺失时生成。** `get` 为空，或 `by_root` 不是非空对象，才生成。已有任意一条根则直接用，避免兜底每次都拉 7 日历史。
2. **复用间隔算法，跳过快照读取。** 对字典里每个根（`parent_id` 为空的事件）走与问预测相同的近 7 日拉史和 `predict_next_for_records`。不读旧快照，否则删除后的空窗会被误当成命中。`status=ok` 的根用现有 `put_root` 写入，TTL 从这次写入重新计算。样本不足的根不写入。
3. **不生成预约条。** 预约仍只在问预测时按事件 id 写入。兜底补的是间隔算法快照。
4. **失败不阻断回答。** 字典拿不到、拉史失败或没有任何成功根时，提示词仍是「无预测算法快照」，模型照常回答，失败再回退硬文案。

## Risks / Trade-offs

- [字典根很多时，一次兜底会按根拉近 7 日历史] → 只在快照缺失时发生；有快照的兜底不加这次开销。
- [前端在 TTL 内改记录，快照仍是旧的] → 接受。新鲜度靠 10 分钟过期，以及 Python 落库成功后的删除；下一次无快照的兜底再生成。
- [生成到一半 Redis 写入失败] → 当次回答按无快照继续，下次兜底再试。
